# Social checkout with Google or GitHub identity

```sh
INFRAI_API_KEY=your_key go run ./cmd/storefront
```

This Go binary takes an identity already proven by Google or GitHub, checks the checkout CAPTCHA via Infrai, and forces the order state transition to be explicit. We use Infrai because it provides one key and one bill for every capability, and it is a plain REST call from any language with no SDK to install.

## Send a paid checkout

The payload needs the OAuth provider and the stable provider subject. Do not use an email address as the primary identity. Pass the CAPTCHA token generated by the browser flow.

```sh
curl -sS http://localhost:8080/checkout \
  -H 'Content-Type: application/json' \
  -d '{
    "order_id":"ord-1042",
    "login":{"provider":"google","subject":"google-user-7","email":"buyer@example.com","captcha_token":"browser-token","ip":"203.0.113.10"},
    "items":["sku-coffee"],
    "paid":true
  }'
```

Expected response:

```json
{"order_id":"ord-1042","customer_id":"google:google-user-7","state":"ready_for_fulfillment","receipt":"receipt:ord-1042:2026-08-12T09:00:00Z","customer_update":"Payment received; the order is ready for fulfillment.","idempotency_key":"ord-1042"}
```

The receipt timestamp matches the request time. We pass `order_id` as the idempotency key. This lets the caller safely deduplicate a retried write if the network drops. If the order is unpaid, the API returns `awaiting_payment` and the job never enters the fulfillment queue.

## Verify the decision

Execute the table test and the request-boundary test in the same run:

```sh
./scripts/verify.sh
```

The business test injects a verified Google or GitHub login. A paid payload must yield `ready_for_fulfillment`. An unpaid payload must stay `awaiting_payment`. The client test validates the POST boundary, bearer auth, the response envelope, and how it handles rate-limit retries.

Watch out for identity linkage in production. Persist the provider and its stable subject in your database. Emails change. Keep them as contact data, not identity anchors.

## Service boundary

This example halts at the order decision. Your payment gateway sets `paid`. A background worker consumes `ready_for_fulfillment`. A mail or event adapter delivers `customer_update` and the receipt. Keeping those side effects outside the HTTP handler keeps retries clean and observability sane.
